# 从点亮屏幕到还原原厂扫词

在有道词典笔 3 上启动 Android，只解决了第一步。要保住这支笔最重要的体验，还要让用户在读书时直接落笔、滑过一行、抬笔看释义，接扫下一行时能把句子连起来。这个操作成了整个移植过程反复使用的实机测试。

## 先让安卓能显示，也能操作

开发从一支已经能通过 ADB 连接的 YDP031CHNSTD 开始。先识别 ARM64 架构、原厂启动槽和分区，再适配 Rockchip Linux 4.4.194 内核与 Android 8.1。屏幕点亮后，第一幅测试画面是色条和黑白棋盘。人在笔上看到稳定的色块，才有了继续检查安卓图形合成和桌面的依据。

触摸也分两步测。先划一道白线，看轨迹是否跟手、坐标方向是否正确；再进入安卓桌面，在计数应用上连点三次，确认显示从 0 变成 3。前一步验证触摸驱动，后一步让输入经过安卓窗口并真正交给应用。后续再接入横屏旋转、返回键和多任务导航。[内核配置与板级修改](../build/kernel) · [显示与输入实测](results.md)

## 扫描头怎样读出完整的一行

原厂扫描的起点是笔尖触点。笔压在纸上时补光灯亮起，沿着字移动时，传感器连续送出图像，抬笔才结束本次采集。早期让笔尖停在纸面等一张预览图，用户看到画面没有更新；换成实际读书时的滑扫动作，我们才验证了按下时连续更新、抬起时停止，以及再次落笔时开始新一行。

最初的通用拼接和 OCR 能出字，整行的开头或结尾却容易缺失。之后接入原厂拼接和 OCR 引擎，让安卓宿主按一次落笔到抬笔的顺序送入图像。验收时从安卓桌面直接起扫，分别扫中文、英文并检查首尾字，再在约一秒内接扫下一行。这既检验了应用唤起时是否漏帧，也检验了两行能否按正确次序合并。[笔尖监听](../build/apps/dictionary/src/local/cherry/originalui/ScanService.java) · [图像与识别引擎之间的传递](../build/apps/dictionary/src/local/cherry/originalui/ScanBridge.java)

接句最容易误判的是时间。第一行识别得慢，并不代表读者已经停笔很久。代码按上一行抬笔和下一行落笔的时间判断是否同组，再将识别文字拼起来。当前源码的判断窗口为两秒，实机教程采用约一秒内接扫的动作。词典结果进入原厂横屏页面，可以继续查看释义、翻译和发音。[接句逻辑](../build/apps/dictionary/src/local/cherry/originalui/ScanSequence.java) · [实机词典截图](results.md#词典)

## 扬声器能响，相机录像为什么还是没声音

开发时，原生相机已经录到了移动画面，回放却听不到说话声。我们先播放两声此前验证过的提示音，确认扬声器能正常播放，再让用户按倒计时先安静、随后说话并轻敲机身，分别检查输入通道。回放第二通道录到的声音时，用户听清了自己说的“测试一二三”。接好系统麦克风输入后，又用原生相机重新录像、回放，最后才确认画面和人声都正常。[相机与音频实测](results.md#外设与性能)

同一个扫描头也用于相机预览、拍照和录像，笔尖灯可以在相机里独立开关。这样，想识别文字时沿纸面滑扫，想保留原始画面时打开原生相机，两种用途都能在笔上直接验证。

## 内存有限时，让用户选择要保留哪个后台

在开发笔上，先用词典再启动游戏会明显变卡，清掉后台后游戏恢复流畅。学习模式因此保留落笔监听和 OCR，游戏模式则退出词典后台，切回学习模式再恢复。一次同机测量中，切换前后的可用内存相差约 113 MiB。实机验收既测试游戏操作，也测试切回来后第一次落笔能否再次弹出词典。[模式界面与实测](results.md#模式切换与阅读)

## 从一支开发笔做成公开安装器

开发笔上先验证了两个方向的切换：在安卓里返回原厂，再点原厂桌面的绿色按钮回到安卓。制作公开安装器时，保留两个原厂 system 分区和 boot B，将安卓数据放入用户分区中的独立文件。每位用户从自己的笔备份和导入资源，自己的序列号与备份共同约束后续写入。[双系统布局](how-it-works.md) · [安装器流程与权限](installation.md)

开发笔的使用体验、磁盘副本上的安装恢复演练、Windows 启动器的自动化测试，各自覆盖不同环节。第二支未经改装设备的首次冷启动和 Windows 直连实机的完整刷入、恢复仍待验证。[分版本的验收记录](results.md)
